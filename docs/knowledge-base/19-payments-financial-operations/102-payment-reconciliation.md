# Payment Reconciliation

**Status:** STABLE — the payments-team-focused view of [`../02-business-workflows/11-merchant-settlement-reconciliation.md`](../02-business-workflows/11-merchant-settlement-reconciliation.md), which remains authoritative. This document restates the process from a "what does Finance actually do with this" angle.

## What reconciliation answers

For every payment SahulatKar's internal `payment_transactions` table says it collected, did the corresponding gateway actually settle that amount to SahulatKar's bank account? And conversely, did the gateway settle anything SahulatKar has no matching internal record for (a signal of either a missed webhook, a fraud pattern, or an integration bug)?

## Process

Daily/scheduled settlement-file pull per gateway → match by `gateway_txn_id` → flag mismatches (amount discrepancy, missing internal record, missing settlement) → surface via `GET /admin/finance/reconciliation` → manual investigation of flagged items.

## Critical caveat (repeated deliberately, since this is the document a finance reader is most likely to open first)

**As of the last code audit, this entire process runs against mock local JSON files, not real gateway data** (`PO-CRIT-02`). Any reconciliation report generated by the current system does not reflect real financial reality. Finance should not rely on `GET /admin/finance/reconciliation` output for actual bookkeeping decisions until this is fixed — and should establish a manual, gateway-portal-based reconciliation process as a stopgap in the meantime, since the automated version cannot currently be trusted.
