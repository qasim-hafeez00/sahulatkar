**Status:** STABLE (screen inventory, from the US-01–US-20 references in module specs) — actual UI/UX detail (wireframes, copy, visual design) does not exist in this repository; this document indexes what screen must exist and what state it reflects, not how it should look.

## What the customer should see at each critical juncture

- **Before signing Murabaha (US-13):** the full cost breakdown — cost price, profit amount, total repayable, complete installment schedule — must be visible and explicit, since this is both a UX requirement and a Shariah/legal disclosure requirement (see [`../04-shariah/17-shariah-product-structure.md`](../04-shariah/17-shariah-product-structure.md)). This is not a "nice to have" screen — the underlying contract cannot even be generated without these fields populated.
- **During checkout execution (US-15):** real-time progress is the intended design (`GET /agent/job/{job_id}/status` is an SSE stream specifically for this) — but since checkout completion is currently an incomplete stub (see [`../05-architecture/microservices/product-service.md`](../05-architecture/microservices/product-service.md)), this screen currently has nothing genuine to report for most orders. UX should have an honest "we're working on it, this may take a while" framing rather than implying a live status that isn't actually being generated by working automation.
- **On any known-gapped transition** (e.g., installment auto-collection not actually firing, refunds not being executable) — the customer-facing copy should not promise behavior the backend can't currently deliver. This is a real near-term UX-writing constraint, not just an engineering caveat.

## Known gap: web-customer is largely unbuilt

Per `docs/PRODUCTION_GAPS_REPORT.md`, `web-customer` is estimated at ~2% complete (scaffold only) as of the last audit — meaning this specification describes required screens, almost none of which are implemented yet.
